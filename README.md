# Конвейер данных на Airflow

Задание 3 по курсу "Прикладные пакеты для анализа данных".

Данные забираются из API, проходят слои stg, dds и cdm в Postgres, а потом выводятся на дашборд в Metabase.

## Структура

```
dags/        DAG-и Airflow
sql/init/    создание баз и схем при первом запуске Postgres
sql/stg/     таблицы слоя stg
sql/dds/     таблицы и загрузка слоя dds
sql/cdm/     витрины
```

## Роли

- Роль 1: docker compose, слой stg, сбор данных, оркестрация
- Роль 2: слой dds, версионирование SCD2, перенос из stg в dds
- Роль 3: витрины cdm, дашборды в Metabase

## Что нужно

- git
- bash и openssl для скрипта `make_env.sh` (есть в macOS, Linux и WSL)
- Docker Desktop (macOS, Windows с WSL2) или Docker Engine с плагином Compose (Linux). Нужен Docker Compose v2.14 или новее, проверить можно командой `docker compose version`
- Для Docker не меньше 4 ГБ памяти, лучше 6-8 ГБ. На macOS это Settings, Resources, Memory в Docker Desktop. На Windows с WSL2 это параметр `memory` в разделе `[wsl2]` файла `%UserProfile%\.wslconfig`. На Linux отдельной настройки нет
- Свободные порты 8080, 15432, 3333
- На Windows команды выполняются в терминале WSL2, а репозиторий лучше клонировать в файловую систему WSL

## Запуск

```bash
git clone https://github.com/AndrewFalse/ppad-lab3.git
cd ppad-lab3
bash make_env.sh
docker compose up -d
```

Первый запуск занимает несколько минут: скачиваются образы, создаются базы. Проверить состояние:

```bash
docker compose ps -a
```

Все сервисы должны быть `healthy`, а `airflow-init` в состоянии `Exited (0)`. Сразу после запуска сервисы ещё проходят проверки, поэтому подождите 1-2 минуты и повторите команду.

## Адреса и доступы

| Что | Адрес | Логин и пароль |
|---|---|---|
| Airflow | http://127.0.0.1:8080 | `AIRFLOW_ADMIN_USER` / `AIRFLOW_ADMIN_PASSWORD` из `.env` |
| Metabase | http://127.0.0.1:3333 | при первом входе Metabase просит создать свою учётную запись |
| Postgres с ноутбука (DBeaver) | 127.0.0.1:15432, база `de` | `etl` / `DWH_ETL_PASSWORD` из `.env` |

Пароли и ключи в `.env` создаёт скрипт `make_env.sh`, сам `.env` в git не попадает (он в `.gitignore`). Если удалить `.env` и создать заново, пароли будут другими, поэтому базы придётся пересоздать командой `docker compose down -v`. Если меняете пароли вручную, используйте только латинские буквы и цифры, не короче 5 символов: пароли подставляются в SQL и в адреса подключений, а Airflow скрывает в логах только секреты от 5 символов.

Пароли ролей и логин администратора Airflow применяются один раз, при первом запуске. Если поменять их в `.env` позже, нужно пересоздать базы командой `docker compose down -v` (все данные удалятся).

Ключи `AIRFLOW_FERNET_KEY`, `MB_ENCRYPTION_SECRET_KEY` и `MB_SESSION_SECRET_KEY` после первого запуска не меняют: ключом Fernet Airflow шифрует подключения и переменные, ключом шифрования Metabase шифрует сохранённые подключения, а ключом сессий подписывает входы. Поэтому `make_env.sh` не перезаписывает уже созданный `.env`.

## Базы и роли

| База | Владелец | Зачем |
|---|---|---|
| `de` | `etl` | хранилище: схемы `stg`, `dds`, `cdm` |
| `airflow` | `airflow` | служебная база Airflow |
| `metabase` | `metabase` | настройки и дашборды Metabase |

- `etl` владеет хранилищем, создаёт и наполняет таблицы всех слоёв. Задачи Airflow подключаются к хранилищу под ним.
- `bi_reader` может читать только схему `cdm`. Под ним Metabase подключается к хранилищу.

Все таблицы в базе `de` создаются только под ролью `etl`, а не под `postgres`. Иначе владельцем таблицы станет суперпользователь: задачи Airflow не смогут её менять, а `bi_reader` не увидит витрину. Открыть psql под `etl`:

```bash
docker compose exec postgres psql -U etl -d de
```

В SQL всегда пишите схему перед именем таблицы (`stg.`, `dds.`, `cdm.`), иначе таблица попадёт в схему `public`.

Базы, роли и схемы создаёт `sql/init/01_init.sh` при первом запуске Postgres. Если скрипт поменялся, базу нужно пересоздать (все данные удалятся):

```bash
docker compose down -v
docker compose up -d
```

Если при первом запуске скрипт упал, после автоматического перезапуска Postgres выполнять его уже не будет, и базы останутся не созданными. В этом случае найдите первую строку `ERROR` в `docker compose logs postgres`, исправьте причину и пересоздайте базы командами выше.

## Подключения

- В Airflow подключение к хранилищу называется `dwh`. Оно задано переменной `AIRFLOW_CONN_DWH` в `docker-compose.yml`, поэтому в разделе Admin, Connections его не видно.
- Логи задач Airflow хранятся в томе Docker `airflow-logs`, поэтому на Linux не нужно настраивать `AIRFLOW_UID`, как в официальной инструкции Airflow.
- В Metabase хранилище добавляется при первой настройке или позже в разделе Admin, Databases: тип PostgreSQL, host `postgres`, port `5432`, база `de`, пользователь `bi_reader`, пароль `DWH_BI_PASSWORD`, в настройке Schemas выбрать только `cdm`. Писать `localhost` нельзя: внутри контейнера это сам Metabase.
- В сборке нет triggerer, поэтому в DAG не используются deferrable-операторы и асинхронные сенсоры.

## Проверка

В Airflow есть служебный DAG `check_dwh`: он проверяет, что подключение `dwh` работает и схемы `stg`, `dds`, `cdm` на месте. Запустить его можно в интерфейсе (включить DAG переключателем и нажать Trigger) или командами:

```bash
docker compose exec airflow-scheduler airflow dags unpause check_dwh
docker compose exec airflow-scheduler airflow dags trigger check_dwh
```

Посмотреть результат:

```bash
docker compose exec airflow-scheduler airflow dags list-runs check_dwh
```

У запуска должно быть состояние `success`.

## Остановка

```bash
docker compose down
```

Данные сохраняются в томах Docker. Команда `docker compose down -v` удаляет их вместе с базами.

## Слой stg: данные Hugging Face

Источник: открытый API Hugging Face Hub (`https://huggingface.co/api`), без токена. Охват задан в `sql/stg/02_orgs.sql`: 20 организаций в трёх группах.

| Группа | Кто | Что собираем |
|---|---|---|
| `labs` | 10 крупных лабораторий: meta-llama, mistralai, Qwen, deepseek-ai, microsoft, ibm-granite, HuggingFaceTB, openai, nvidia, stabilityai | снимок, коммиты, ревизии |
| `ru` | 8 российских организаций и авторов: ai-forever, yandex, t-tech, deepvk, MTSAIR, Vikhrmodels, IlyaGusev, cointegrated | снимок, коммиты, ревизии |
| `quant` | 2 перераспространителя квантизованных копий: unsloth, bartowski | только ежедневный снимок, без истории коммитов |

Данные собирает DAG `hf_pipeline`, группа задач `extract`, по порядку: `create_stg_tables`, `load_license_tags`, `load_models`, `load_commits`, `load_revisions`, `load_base_models`, `check_stg`. Пока у DAG нет расписания (`schedule=None`), его запускают вручную; расписание включается на следующем этапе.

| Таблица | Одна строка | Как обновляется | Ключ |
|---|---|---|---|
| `stg.hf_orgs` | организация из охвата, `stratum` это её группа (`labs`, `ru` или `quant`) | перезаписывается при каждом запуске из `02_orgs.sql` | `org` |
| `stg.hf_models` | модель в снимке за день, `payload` это объект из `GET /api/models` вместе со списком файлов `siblings` | снимок организации за день перезаписывается целиком | `business_date`, `payload->>'_id'` |
| `stg.hf_list_runs` | сколько страниц и моделей пришло по организации в снимке | вместе со снимком | `business_date`, `org` |
| `stg.hf_commits` | коммит модели из `GET /api/models/{id}/commits/main` | добавляются только новые коммиты | `hf_id`, `sha` |
| `stg.hf_revisions` | карточка и список файлов модели на коммит из `GET /api/models/{id}/revision/{sha}` | добавляются только для новых коммитов | `hf_id`, `sha` |
| `stg.hf_base_models` | базовая модель из `cardData.base_model`, которой нет в снимке дня: модель другой организации или переименованная либо удалённая модель из охвата | добавляются только новые | `repo_id` |
| `stg.hf_license_tags` | справочник лицензий из `GET /api/models-tags-by-type?type=license`, `payload` вида `{"license": [...]}` | перезаписывается за день | `business_date` |

Служебные поля:

- `business_date` (есть в `stg.hf_models`, `stg.hf_list_runs`, `stg.hf_license_tags`) это дата снимка в UTC, она берётся из `run_after` запуска;
- `source` это эндпоинт API, из которого пришли данные (у `stg.hf_orgs` это `seed sql/stg/02_orgs.sql`);
- `load_id` это `run_id` запуска Airflow (у `stg.hf_orgs` его нет);
- `loaded_at` это время записи.

Как связать таблицы:

- `stg.hf_commits.hf_id` и `stg.hf_revisions.hf_id` равны `stg.hf_models.payload->>'_id'`.
- Текущая ревизия модели это строка `stg.hf_revisions`, у которой пара `hf_id`, `sha` равна паре `payload->>'_id'`, `payload->>'sha'` модели в снимке.
- Ревизия и коммит связаны парой `hf_id`, `sha`.

Как обновляется снимок:

- Снимок за день перезаписывается по каждой организации отдельно, в своей транзакции. Если запуск упал на середине, у уже загруженных организаций данные новые, а у остальных прежние.
- Полный снимок дня это дата, за которую в `stg.hf_list_runs` есть 20 строк и у всех `models` больше 0. Проверочные запуски на нескольких организациях дают неполный снимок, поэтому «последний снимок» нужно брать по последней полной дате.
- Модель считается удалённой или скрытой, только если её нет в снимке дня, где у её организации есть строка в `stg.hf_list_runs`.
- API отдаёт только текущее состояние моделей, поэтому снимок делается только свежим запуском. Задачи `load_license_tags` и `load_models` сами падают, если запуск не сегодняшний: перезапуск старого запуска (Clear) записал бы сегодняшние данные под старой датой. Поэтому у DAG нет backfill и `catchup=False`.

Откуда история для SCD2:

- У открытых моделей групп `labs` и `ru` история берётся из коммитов и ревизий: каждая ревизия это состояние карточки и файлов на коммит, дата коммита лежит в `payload->>'date'` таблицы `stg.hf_commits` и в `payload->>'lastModified'` ревизии.
- У закрытых моделей (`gated` равно `"auto"` или `"manual"`) коммиты и ревизии мы не загружаем, а у группы `quant` не загружаем намеренно. Их история есть только по ежедневным снимкам, начиная с первого запуска.

Что важно знать при разборе данных в dds:

- `payload->>'_id'` это стабильный ключ модели, он не меняется при переименовании. `payload->>'id'` это имя вида `org/name`, оно может меняться.
- В коммите (`stg.hf_commits.payload`) лежат `id` (это sha), `title`, `message`, `authors` (список, у каждого автора есть `user`, это срез «редактор») и `date` (дата коммита). Колонка `commit_number` это порядковый номер коммита в истории модели, 1 самый первый. По нему упорядочивают версии, если у коммитов одинаковые даты.
- `cardData.license` бывает строкой или списком, `cardData.base_model` тоже. Если лицензия `other`, её название и ссылка лежат в `license_name` и `license_link`.
- `createdAt` у старых моделей равен `2022-03-02T23:29:04.000Z` или `2022-03-02T23:29:05.000Z`. Это не настоящая дата создания, а день, с которого Hugging Face хранит даты.
- `downloads` это скачивания за последние 30 дней, `likes` это текущие лайки. Они меняются каждый день, поэтому это факты снимка, а не атрибуты для версий SCD2.
- В `stg.hf_revisions` кроме ключей модели `_id` и `id` лежат `cardData`, `siblings` (список файлов), `sha`, `lastModified` (дата коммита), `pipeline_tag`, `library_name` и `tags`. Первые шесть полей исторические, то есть такие, какими были на этот коммит. В `tags` часть тегов (`region:*`, `deploy:*`, `eval-results`) показывает текущее состояние, поэтому для версий SCD2 лучше брать `cardData`, признаки из `siblings`, `pipeline_tag` и `library_name`, а не `tags` целиком. Признак `gated` по коммитам не восстанавливается.
- Базовая модель загружается один раз, при первом упоминании в карточке, и потом не обновляется: для сравнения лицензий этого хватает на срок лабы. `repo_id` в `stg.hf_base_models` это имя из карточки; если модель переименована, актуальное имя лежит в `payload->>'id'`.
- `http_status` в `stg.hf_revisions` и `stg.hf_base_models`: 200 ответ получен, 401 модель закрыта, удалена или недоступна без входа, 404 нет такой ревизии или модели. Другие коды тоже возможны и сохраняются как есть. При коде не 200 `payload` равен NULL.
- Если Hugging Face переписал историю модели (такое бывает редко), старые коммиты остаются в `stg.hf_commits`. Версии строятся по коммитам, у которых есть ревизия с кодом 200.
- `create table if not exists` не добавляет новые колонки в уже созданные таблицы, поэтому новые колонки добавляются в `01_create_tables.sql` командой `alter table ... add column if not exists`.

Пример: лицензии моделей в последнем полном снимке.

```sql
select payload->>'id' as repo_id, payload->'cardData'->>'license' as license
from stg.hf_models
where business_date = (
    select max(business_date) from (
        select business_date from stg.hf_list_runs
        group by business_date
        having count(*) = (select count(*) from stg.hf_orgs) and min(models) > 0
    ) full_days
);
```

## Запуск сбора данных

Проверочный запуск на нескольких организациях:

```bash
docker compose exec airflow-scheduler airflow dags unpause hf_pipeline
docker compose exec airflow-scheduler airflow dags trigger hf_pipeline --conf '{"orgs": ["yandex", "deepvk"]}'
```

Полный запуск по всем 20 организациям: кнопка Trigger в интерфейсе без параметров или та же команда без `--conf`. Первый полный запуск долгий (по оценке 5-6 часов), потому что он загружает историю коммитов и ревизий всех открытых моделей групп `labs` и `ru`. Задачи можно перезапускать, пока не наступил следующий день по UTC: уже загруженные коммиты, ревизии и базовые модели повторно не скачиваются, а снимок списка моделей и справочник лицензий скачиваются заново (около 30 запросов). У моделей, где появился новый коммит, список коммитов запрашивается заново, но записываются только новые. Если день уже сменился, запустите новый запуск вместо перезапуска старого.

Без токена Hugging Face разрешает 500 запросов к API за 5 минут с одного IP. Клиент `dags/hf_api.py` сам ждёт нового окна, но не запускайте сбор одновременно с нескольких ноутбуков в одной сети.

Задача `extract.check_stg` в конце проверяет, что снимок по каждой организации есть и не задвоен, у коммитов есть даты, у ревизий есть свои коммиты, а `payload` заполнен ровно у ответов с кодом 200. Если проверка не прошла, запуск DAG помечается как упавший. В её логе две строки со счётчиками. В первой `models` это весь снимок дня, а коммиты, ревизии и базовые модели посчитаны за всё время. Во второй открытые модели групп `labs` и `ru` в снимке дня без коммита на текущий sha, коммиты без ревизии за всё время и базовые модели с кодом не 200. Эти счётчики не роняют проверку, но показывают, всё ли догрузилось.

Если задача сбора раз за разом падает на одном и том же месте (постоянная ошибка 5xx на стороне Hugging Face или недопустимый символ в ответе), причина видна в конце лога задачи: при ошибке 5xx или 408 там адрес запроса (у коммитов, ревизий и базовых моделей в нём есть имя модели, у снимка только адрес списка моделей), при ошибке записи в базу текст ошибки Postgres. Отдельного механизма пропуска модели нет: можно запустить сбор с `--conf` без организации этой модели или дождаться исправления на стороне Hugging Face.
