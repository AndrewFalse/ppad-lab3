# ППАД, задание 3: конвейер Airflow, Postgres, Metabase

Тема: документация и лицензии открытых ИИ-моделей на Hugging Face.
Поток данных: API Hugging Face → `stg` → `dds` → `cdm` → дашборд в Metabase.

## Запуск

Нужен Docker (не меньше 4 ГБ памяти, лучше 6-8 ГБ). На Windows всё выполняется в терминале WSL2.

```bash
git clone https://github.com/AndrewFalse/ppad-lab3.git
cd ppad-lab3
bash make_env.sh
docker compose up -d
```

`make_env.sh` создаёт `.env` с паролями. Через 1-2 минуты `docker compose ps` покажет все сервисы `healthy`.

Затем положите в папку репозитория файл дампа `stg_20261006.dump` (его даёт роль 1), восстановите его и только потом включите DAG:

```bash
docker compose exec -T postgres pg_restore -U etl -d de --no-owner --clean --if-exists < stg_20261006.dump
docker compose exec airflow-scheduler airflow dags unpause hf_pipeline
```

Если включить DAG без дампа, начнётся загрузка всей истории на 6-7 часов.

| Что | Адрес | Доступ |
|---|---|---|
| Airflow | http://127.0.0.1:8080 | `AIRFLOW_ADMIN_USER` / `AIRFLOW_ADMIN_PASSWORD` из `.env` |
| Metabase | http://127.0.0.1:3333 | учётная запись создаётся при первом входе |
| Postgres | 127.0.0.1:15432, база `de` | `etl` / `DWH_ETL_PASSWORD` из `.env` |

## DAG hf_pipeline

Запускается каждый день в 03:00 UTC (06:00 по Москве). Группы задач идут по очереди:

`extract` (сбор в stg, готово) → `dds` → `dq` → `cdm`

Группы `dds`, `dq` и `cdm` выполняют SQL-файлы из папок `sql/dds/`, `sql/dq/`, `sql/cdm/` по порядку имён. Python трогать не нужно: кладёте файл, через минуту он появляется в DAG.

## Кто что делает

| Роль | Где | Что |
|---|---|---|
| 2 | `sql/dds/` | слой dds из stg, версии SCD2 |
| 2 | `sql/dq/` | проверки dds |
| 3 | `sql/cdm/` | витрины из dds |
| 3 | Metabase | подключение: host `postgres`, port `5432`, база `de`, пользователь `bi_reader`, пароль `DWH_BI_PASSWORD`, схема `cdm`; дашборд |

## Правила для SQL-файлов

- Имя: `01_name.sql`, `02_name.sql`. Номер из двух цифр, только латиница, цифры и `_`, имя `start.sql` занято.
- Один файл выполняется в одной транзакции. Повторный запуск должен давать тот же результат: `create table if not exists`, перед вставкой `delete` или `truncate`.
- Всегда пишите схему: `dds.table`, `cdm.table`. Таблицы создаются только под ролью `etl`, тогда Metabase их видит.
- Дата снимка в SQL: `'{{ dag_run.run_after.strftime("%Y-%m-%d") }}'`. Шаблон `{{ ds }}` не работает.
- Проверка в `sql/dq/` это один `select`, который возвращает одну строку, где все значения `true`. Например: `select count(*) = 0 as ok from dds.dim_model where ...`. Если проверка не прошла, витрины не пересчитываются.
- Проверить новый файл: `docker compose exec airflow-scheduler airflow dags trigger hf_pipeline --conf '{"orgs": ["yandex"]}'` (сбор только по одной организации, займёт пару минут).

## Данные в stg

`payload` это JSON из ответа API как есть.

| Таблица | Что лежит | Ключ |
|---|---|---|
| `stg.hf_orgs` | 20 организаций и группа: `labs`, `ru`, `quant` | `org` |
| `stg.hf_models` | снимок моделей за день | `business_date`, `payload->>'_id'` |
| `stg.hf_list_runs` | сколько моделей пришло по организации за день | `business_date`, `org` |
| `stg.hf_commits` | коммиты моделей, `commit_number` 1 это первый коммит | `hf_id`, `sha` |
| `stg.hf_revisions` | карточка и список файлов модели на каждый коммит | `hf_id`, `sha` |
| `stg.hf_base_models` | базовые модели, которых нет в снимке | `repo_id` |
| `stg.hf_license_tags` | справочник лицензий Hugging Face | `business_date` |

Главное для dds:

- Ключ модели `hf_id`, он равен `payload->>'_id'` и не меняется при переименовании.
- История версий берётся из `stg.hf_revisions`: дата версии `payload->>'lastModified'`, порядок по `commit_number`. У закрытых моделей (`gated` равно `auto` или `manual`) и у группы `quant` коммитов нет, их история только по ежедневным снимкам.
- Лицензия: `payload->'cardData'->'license'`, бывает строкой или списком. При `other` смотрите `license_name` и `license_link`. `base_model` тоже строка или список.
- Для версий SCD2 берите `cardData`, `siblings` (файлы), `pipeline_tag`, `library_name`. `downloads` и `likes` меняются каждый день, это факты снимка.
- Полный снимок дня: в `stg.hf_list_runs` за дату 20 строк и у всех `models` больше 0. Проверочные запуски дают неполный снимок.
- `createdAt` равный `2022-03-02T23:29:0...` у старых моделей ненастоящий.
- Если `http_status` не 200, `payload` равен NULL.

## Если что-то сломалось

- Упала `extract.check_stg`: запустите DAG заново.
- Ошибка `this run is not from today`: не нажимайте Clear у вчерашних запусков, запустите новый.
- Упала задача в `dds`, `dq` или `cdm`: исправьте SQL и нажмите Clear у этой задачи в сегодняшнем запуске.
- `No space left on device`: освободите место на диске и перезапустите Docker Desktop.
- Не запускайте сбор одновременно с двух ноутбуков в одной сети.

Остановить: `docker compose down` (данные сохраняются). `docker compose down -v` удаляет базы.

## Слой CDM и Дашборд 

Слой витрин данных (`cdm`) состоит из 7 SQL-файлов, которые лежат в папке `sql/cdm/`. 
Они автоматически выполняются в DAG `hf_pipeline` после успешного прохождения слоев `dds` и `dq`.

### Витрины в схеме `cdm`:
1. `dim_license` — справочник лицензий с человекочитаемыми названиями.
2. `dm_license_distribution` — распределение текущих моделей по лицензиям и стратам (labs, ru, quant), с суммарными скачиваниями и лайками.
3. `dm_org_stats` — сводка по организациям: количество моделей, популярность, число закрытых (gated) моделей и доля документированных.
4. `dm_model_documentation` — документированность моделей (наличие README, LICENSE) в разрезе типов задач (pipeline_tag) и страт.
5. `dm_daily_metrics` — ежедневная динамика: количество моделей, суммарные downloads, likes, число закрытых и приватных моделей.
6. `dm_license_changes` — история смены лицензий моделями (использует SCD2-версионирование из `dds.dim_model`).
7. `dm_weight_formats` — популярность форматов весов (safetensors, bin, gguf и др.) в разрезе организаций.

Все витрины идемпотентны: при повторном запуске они пересчитываются заново (`truncate` + `insert`), не создавая дублей.

### Подключение Metabase
1. Открой Metabase: http://127.0.0.1:3333
2. При первом входе создай аккаунт администратора.
3. Перейди в **Admin settings** → **Databases** → **Add a database**.
4. Заполни параметры:
   - **Database type**: PostgreSQL
   - **Name**: DWH
   - **Host**: `postgres` (важно: не `localhost`)
   - **Port**: `5432`
   - **Database name**: `de`
   - **Username**: `bi_reader`
   - **Password**: значение `DWH_BI_PASSWORD` из файла `.env`
5. В разделе **Advanced options** → **Schemas** укажи `cdm`, чтобы Metabase не показывал системные таблицы.
6. Нажми **Save**, затем **Sync database** и **Sync schema**.


### Важное примечание о пропущенных датах
В `dm_daily_metrics` могут отсутствовать данные за некоторые дни. Это связано с тем, что проект развернут локально в Docker. 
Параметр `catchup=False` в DAG отключает догон пропущенных дней, чтобы не перегружать API Hugging Face. Поэтому сбор данных происходит только в те дни, когда контейнеры запущены. 
Исторические данные за 5–6 октября взяты из дампа `stg_20261006.dump`, а ежедневный автоматический сбор начался с 19 октября после включения DAG.

### Что можно увидеть на дашборде
Дашборд «Документация и лицензии открытых ИИ-моделей на Hugging Face» собран из витрин схемы `cdm` и содержит следующие аналитические блоки:

1. **Топ-10 организаций по скачиваниям** (`dm_org_stats`)
   * **Тип:** Столбчатая диаграмма.
   * **Что показывает:** Лидеров по суммарному количеству скачиваний (downloads) их моделей. 
   * **Аналитика:** Позволяет увидеть, что основную популярность генерируют крупные лаборатории (например, `microsoft`), в то время как многие российские и квантованные организации имеют значительно меньший объем загрузок.

2. **Распределение текущих моделей по лицензиям** (`dm_license_distribution`)
   * **Тип:** Кольцевая диаграмма (Donut chart).
   * **Что показывает:** Долю каждой лицензии среди всех актуальных моделей.
   * **Аналитика:** Наглядно демонстрирует доминирование лицензии `apache-2.0` (39%), за которой следует `other` (20.9%). Категория `unknown` (13.9%) показывает долю моделей, авторы которых не указали лицензию в карточке, что является риском для их использования.

3. **Лицензии по стратам** (`dm_license_distribution`)
   * **Тип:** Столбчатая диаграмма.
   * **Что показывает:** Количество моделей в разрезе групп (`labs` — крупные лаборатории, `ru` — российские, `quant` — квантованные копии).
   * **Аналитика:** Показывает, что сегмент `quant` (квантованные модели) и `labs` (оригинальные модели) примерно сопоставимы по количеству, а сегмент `ru` пока значительно меньше.

4. **Популярные форматы весов** (`dm_weight_formats`)
   * **Тип:** Столбчатая диаграмма.
   * **Что показывает:** Частоту встречаемости различных форматов файлов весов (`safetensors`, `gguf`, `bin`, `pt` и др.).
   * **Аналитика:** Подтверждает индустриальный тренд: `safetensors` (безопасный формат) и `gguf` (для локального запуска) значительно опережают устаревший формат `bin` (PyTorch).

5. **Топ организаций по смене лицензий** (`dm_license_changes`)
   * **Тип:** Столбчатая диаграмма.
   * **Что показывает:** Организации, чьи модели чаще всего меняли лицензию (на основе SCD2-версионирования).
   * **Аналитика:** Лидером является `nvidia` (более 120 смен). Это может указывать на частые изменения в политике лицензирования их открытых моделей.

6. **Матрица переходов лицензий** (`dm_license_changes`)
   * **Тип:** Сводная таблица (Pivot Table).
   * **Что показывает:** С какой лицензии на какую переходили модели (по строкам — старая лицензия, по столбцам — новая).
   * **Аналитика:** Большинство изменений (119 случаев) — это уточнение или смена лицензии внутри `apache-2.0`. Также видны переходы с `cc-by-nc-sa-4.0` на `apache-2.0`, что говорит о смягчении условий использования моделей.

7. **Документированность по типам задач (Топ-15)** (`dm_model_documentation`)
   * **Тип:** Столбчатая диаграмма.
   * **Что показывает:** Долю моделей с наличием README или LICENSE в разрезе типов задач (`pipeline_tag`).
   * **Аналитика:** Показывает, насколько ответственно авторы относятся к документации в зависимости от сферы применения модели (например, для `text-generation` документации больше, чем для узкоспециализированных задач).

8. **Динамика скачиваний и лайков** (`dm_daily_metrics`)
   * **Тип:** Линейный график (Line chart).
   * **Что показывает:** Изменение суммарных скачиваний и лайков по датам.
   * **Аналитика:** *Примечание:* Резкие перепады на графике обусловлены тем, что в дампе были исторические данные за 5–6 октября, а следующий сбор произошел только 19 октября (после включения DAG). Настройка `catchup=False` предотвращает автоматический догон пропущенных дней, поэтому линия имеет разрывы. Данные за пропущенные дни отсутствуют, так как локальные контейнеры Docker не были запущены.
