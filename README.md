# Конвейер данных на Airflow

Задание 3 по курсу "Прикладные пакеты для анализа данных".

Данные забираются из API, проходят слои stg, dds и cdm в Postgres, а потом выводятся на дашборд в Metabase.

## Структура

```
dags/        DAG-и Airflow
sql/init/    создание баз и схем при первом запуске Postgres
sql/stg/     таблицы слоя stg
sql/dds/     таблицы и загрузка слоя dds
sql/cdm/     витрины
```

## Роли

- Роль 1: docker compose, слой stg, сбор данных, оркестрация
- Роль 2: слой dds, версионирование SCD2, перенос из stg в dds
- Роль 3: витрины cdm, дашборды в Metabase

## Что нужно

- git
- bash и openssl для скрипта `make_env.sh` (есть в macOS, Linux и WSL)
- Docker Desktop (macOS, Windows с WSL2) или Docker Engine с плагином Compose (Linux). Нужен Docker Compose v2.14 или новее, проверить можно командой `docker compose version`
- Для Docker не меньше 4 ГБ памяти, лучше 6-8 ГБ. На macOS это Settings, Resources, Memory в Docker Desktop. На Windows с WSL2 это параметр `memory` в разделе `[wsl2]` файла `%UserProfile%\.wslconfig`. На Linux отдельной настройки нет
- Свободные порты 8080, 15432, 3333
- На Windows команды выполняются в терминале WSL2, а репозиторий лучше клонировать в файловую систему WSL

## Запуск

```bash
git clone https://github.com/AndrewFalse/ppad-lab3.git
cd ppad-lab3
bash make_env.sh
docker compose up -d
```

Первый запуск занимает несколько минут: скачиваются образы, создаются базы. Проверить состояние:

```bash
docker compose ps -a
```

Все сервисы должны быть `healthy`, а `airflow-init` в состоянии `Exited (0)`. Сразу после запуска сервисы ещё проходят проверки, поэтому подождите 1-2 минуты и повторите команду.

## Адреса и доступы

| Что | Адрес | Логин и пароль |
|---|---|---|
| Airflow | http://127.0.0.1:8080 | `AIRFLOW_ADMIN_USER` / `AIRFLOW_ADMIN_PASSWORD` из `.env` |
| Metabase | http://127.0.0.1:3333 | при первом входе Metabase просит создать свою учётную запись |
| Postgres с ноутбука (DBeaver) | 127.0.0.1:15432, база `de` | `etl` / `DWH_ETL_PASSWORD` из `.env` |

Пароли и ключи в `.env` создаёт скрипт `make_env.sh`, сам `.env` в git не попадает (он в `.gitignore`). Если удалить `.env` и создать заново, пароли будут другими, поэтому базы придётся пересоздать командой `docker compose down -v`. Если меняете пароли вручную, используйте только латинские буквы и цифры, не короче 5 символов: пароли подставляются в SQL и в адреса подключений, а Airflow скрывает в логах только секреты от 5 символов.

Пароли ролей и логин администратора Airflow применяются один раз, при первом запуске. Если поменять их в `.env` позже, нужно пересоздать базы командой `docker compose down -v` (все данные удалятся).

Ключи `AIRFLOW_FERNET_KEY`, `MB_ENCRYPTION_SECRET_KEY` и `MB_SESSION_SECRET_KEY` после первого запуска не меняют: ключом Fernet Airflow шифрует подключения и переменные, ключом шифрования Metabase шифрует сохранённые подключения, а ключом сессий подписывает входы. Поэтому `make_env.sh` не перезаписывает уже созданный `.env`.

## Базы и роли

| База | Владелец | Зачем |
|---|---|---|
| `de` | `etl` | хранилище: схемы `stg`, `dds`, `cdm` |
| `airflow` | `airflow` | служебная база Airflow |
| `metabase` | `metabase` | настройки и дашборды Metabase |

- `etl` владеет хранилищем, создаёт и наполняет таблицы всех слоёв. Задачи Airflow подключаются к хранилищу под ним.
- `bi_reader` может читать только схему `cdm`. Под ним Metabase подключается к хранилищу.

Все таблицы в базе `de` создаются только под ролью `etl`, а не под `postgres`. Иначе владельцем таблицы станет суперпользователь: задачи Airflow не смогут её менять, а `bi_reader` не увидит витрину. Открыть psql под `etl`:

```bash
docker compose exec postgres psql -U etl -d de
```

В SQL всегда пишите схему перед именем таблицы (`stg.`, `dds.`, `cdm.`), иначе таблица попадёт в схему `public`.

Базы, роли и схемы создаёт `sql/init/01_init.sh` при первом запуске Postgres. Если скрипт поменялся, базу нужно пересоздать (все данные удалятся):

```bash
docker compose down -v
docker compose up -d
```

Если при первом запуске скрипт упал, после автоматического перезапуска Postgres выполнять его уже не будет, и базы останутся не созданными. В этом случае найдите первую строку `ERROR` в `docker compose logs postgres`, исправьте причину и пересоздайте базы командами выше.

## Подключения

- В Airflow подключение к хранилищу называется `dwh`. Оно задано переменной `AIRFLOW_CONN_DWH` в `docker-compose.yml`, поэтому в разделе Admin, Connections его не видно.
- Логи задач Airflow хранятся в томе Docker `airflow-logs`, поэтому на Linux не нужно настраивать `AIRFLOW_UID`, как в официальной инструкции Airflow.
- В Metabase хранилище добавляется при первой настройке или позже в разделе Admin, Databases: тип PostgreSQL, host `postgres`, port `5432`, база `de`, пользователь `bi_reader`, пароль `DWH_BI_PASSWORD`, в настройке Schemas выбрать только `cdm`. Писать `localhost` нельзя: внутри контейнера это сам Metabase.
- В сборке нет triggerer, поэтому в DAG не используются deferrable-операторы и асинхронные сенсоры.

## Проверка

В Airflow есть служебный DAG `check_dwh`: он проверяет, что подключение `dwh` работает и схемы `stg`, `dds`, `cdm` на месте. Запустить его можно в интерфейсе (включить DAG переключателем и нажать Trigger) или командами:

```bash
docker compose exec airflow-scheduler airflow dags unpause check_dwh
docker compose exec airflow-scheduler airflow dags trigger check_dwh
```

Посмотреть результат:

```bash
docker compose exec airflow-scheduler airflow dags list-runs check_dwh
```

У запуска должно быть состояние `success`.

## Остановка

```bash
docker compose down
```

Данные сохраняются в томах Docker. Команда `docker compose down -v` удаляет их вместе с базами.

## Слой stg: данные Hugging Face

Источник: открытый API Hugging Face Hub (`https://huggingface.co/api`), без токена. Охват: 18 организаций из `sql/stg/02_orgs.sql`, крупные лаборатории (`labs`) и российские организации и авторы (`ru`). Данные собирает DAG `hf_pipeline`, группа задач `extract`.

| Таблица | Одна строка | Как обновляется | Ключ |
|---|---|---|---|
| `stg.hf_orgs` | организация из охвата и её группа (`labs` или `ru`) | перезаписывается при каждом запуске из `02_orgs.sql` | `org` |
| `stg.hf_models` | модель в снимке за день, `payload` это объект из `GET /api/models` | снимок организации за день перезаписывается целиком | `business_date`, `payload->>'_id'` |
| `stg.hf_list_runs` | сколько страниц и моделей пришло по организации в снимке | вместе со снимком | `business_date`, `org` |
| `stg.hf_commits` | коммит модели из `GET /api/models/{id}/commits/main` | добавляются только новые коммиты | `hf_id`, `sha` |
| `stg.hf_revisions` | карточка и список файлов модели на коммит из `GET /api/models/{id}/revision/{sha}` | добавляются только для новых коммитов | `hf_id`, `sha` |
| `stg.hf_base_models` | базовая модель из `cardData.base_model`, которой нет в охвате | добавляются только новые | `repo_id` |
| `stg.hf_license_tags` | справочник лицензий из `GET /api/models-tags-by-type?type=license` | перезаписывается за день | `business_date` |

Служебные поля: `business_date` (есть в `stg.hf_models`, `stg.hf_list_runs`, `stg.hf_license_tags`) это дата снимка в UTC, она берётся из `run_after` запуска; `source` это эндпоинт API, из которого пришли данные (у `stg.hf_orgs` это `seed sql/stg/02_orgs.sql`); `load_id` это `run_id` запуска Airflow (у `stg.hf_orgs` его нет); `loaded_at` это время записи.

Как обновляется снимок:

- Снимок за день перезаписывается по каждой организации отдельно, в своей транзакции. Если запуск упал на середине, у уже загруженных организаций данные новые, а у остальных прежние. Какие организации загружены за день, видно в `stg.hf_list_runs`.
- API отдаёт только текущее состояние моделей, поэтому снимок делается только свежим запуском. Перезапуск старого запуска (Clear) записал бы сегодняшние данные под старой датой, поэтому у DAG нет backfill и `catchup=False`. История изменений берётся не из снимков, а из коммитов и ревизий.

Что важно знать при разборе данных в dds:

- `payload->>'_id'` это стабильный ключ модели, он не меняется при переименовании. `payload->>'id'` это имя вида `org/name`, оно может меняться.
- `gated` бывает `false`, `"auto"` или `"manual"`. У закрытых моделей (`auto`, `manual`) коммиты и ревизии без входа недоступны, поэтому их история есть только по ежедневным снимкам.
- `cardData.license` бывает строкой или списком, `cardData.base_model` тоже. Если лицензия `other`, её название и ссылка лежат в `license_name` и `license_link`.
- `createdAt` у старых моделей равен `2022-03-02T23:29:04.000Z` или `2022-03-02T23:29:05.000Z`. Это не настоящая дата создания, а день, с которого Hugging Face хранит даты.
- `downloads` это скачивания за последние 30 дней, `likes` это текущие лайки. Они меняются каждый день, поэтому это факты снимка, а не атрибуты для версий SCD2.
- В `stg.hf_revisions` кроме ключей модели `_id` и `id` лежат только поля, которые относятся к коммиту: `cardData`, `siblings` (список файлов), `sha`, `lastModified` (дата коммита), `tags`, `pipeline_tag`, `library_name`. Признак `gated` по коммитам не восстанавливается.
- Базовая модель загружается один раз, при первом упоминании в карточке, и потом не обновляется: для сравнения лицензий этого хватает на срок лабы. `repo_id` в `stg.hf_base_models` это имя из карточки; если модель переименована, актуальное имя лежит в `payload->>'id'`.
- `http_status` в `stg.hf_revisions` и `stg.hf_base_models`: 200 ответ получен, 401 модель закрыта, удалена или недоступна без входа, 404 такой ревизии нет. При коде не 200 `payload` равен NULL.

Пример: лицензии моделей в последнем снимке.

```sql
select payload->>'id' as repo_id, payload->'cardData'->>'license' as license
from stg.hf_models
where business_date = (select max(business_date) from stg.hf_list_runs);
```

## Запуск сбора данных

Проверочный запуск на нескольких организациях:

```bash
docker compose exec airflow-scheduler airflow dags unpause hf_pipeline
docker compose exec airflow-scheduler airflow dags trigger hf_pipeline --conf '{"orgs": ["yandex", "deepvk"]}'
```

Полный запуск по всем 18 организациям: кнопка Trigger в интерфейсе без параметров или та же команда без `--conf`. Первый полный запуск долгий (несколько часов), потому что он загружает историю коммитов и ревизий всех открытых моделей. Задачи можно перезапускать: уже загруженные коммиты, ревизии и базовые модели повторно не скачиваются, а снимок списка моделей и справочник лицензий скачиваются заново (это около 30 запросов).

Без токена Hugging Face разрешает 500 запросов к API за 5 минут с одного IP. Клиент `dags/hf_api.py` сам ждёт нового окна, но не запускайте сбор одновременно с нескольких ноутбуков в одной сети.

Задача `extract.check_stg` в конце проверяет, что снимок по каждой организации есть и не задвоен, у коммитов есть даты, а у ревизий есть свои коммиты. Если проверка не прошла, запуск DAG помечается как упавший. В её логе строка `models ... commits ... revisions ...`: `models` это весь снимок дня, а коммиты, ревизии и базовые модели посчитаны за всё время. Ответы не 200 в ревизиях не роняют проверку, но видны в этой строке и в логе задачи `load_revisions`.
